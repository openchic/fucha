## Context

依赖 change 2 的 ThemeToken 契约、generateCss 单源管线与预览宿主。对应里程碑 M2。存储沿用既定决策：不引 electron-store，userData 下 JSON 文件 fs 读写。

## Goals / Non-Goals

**Goals:**

- 面板逐项调 token，实时反映，另存自定义主题
- 自定义主题与偏好的文件持久化（改名、删、导入导出）
- deriveToken 自动建议（取主色 + 选预设，可见可改可还原）

**Non-Goals:**

- 多预设库扩充、主题分享
- 从源站学排版（已明确不做）
- 取色器 / 滑杆以外的编辑交互形式

## Decisions

**面板状态走"会话草稿 + 显式另存"。** 面板编辑改的是内存中的工作副本（内置预设的副本或自定义主题的副本），实时喂给预览；只有"另存为"才落盘。关闭或切换时的未保存调整给出提示。备选"改动即自动保存"：误操作直接污染已存主题，恢复成本高，否。

**存储布局：目录即主题。** `userData/themes/<id>/token.json`，偏好 `userData/preferences.json`（记 lastThemeId）。目录式便于导出（拷目录）与未来扩展元信息（重命名写同目录 meta）。所有读写经主进程 IPC（renderer 无 fs 权限），导入校验复用 theme-tokens 的校验函数。备选单文件聚合：重命名与删除变成全量重写，否。

**入口跟随行为，面板开左列。** 主题下拉即列表（内置预设加自定义主题），底部两个动作项（编辑当前主题、管理自定义主题）闭环入口，不发明新控件；面板本体开在左列，编辑时元信息折叠让位。硬约束是预览不被遮挡——右侧抽屉与弹层都会遮住预览，实时反馈闭环就断了。备选操作栏加"编辑主题"图标：主题能力拆成两处且工具栏膨胀，否。

**滑杆范围直接取 token 契约的字段边界。** 范围与校验共用同一张常量表（text.fontSize 15-17、lineHeight 1.5-2.2、h1 18-26 等），面板不另立一套边界，避免调得出但校验不过的死角。颜色项取色器，数值项滑杆。

**deriveToken 纯函数，输入 Article 元信息与内容特征。** 主色：cover（og:image）或 favicon 经 canvas 缩采样后做简单量化聚类取主簇，转 HSL 后做饱和度与明度归一（品牌色直接当主色常常过艳）；内容特征：代码块与表格占正文比重阈值判型，映射到内置预设基底。输出 `Partial<ThemeToken>` 只含颜色族，排版字段一律不输出——与规格的"明确边界"对应。对比度阈值 3.0，因主色只上装饰元素（#8fae96 这类低对比色正是该被拦下的典型）。

**对比度校验用 WCAG 对比度计算。** 提取色与 token 背景色算对比度，阈值取 3.0（装饰性色条的标准），不达标降级默认主色。自实现约二十行，不引库。

**建议的呈现是"应用建议"按钮，不是自动切换。** derive 结果在面板顶部以建议条呈现（提取到的主色色块 + 基于哪个预设），点应用才把建议并入工作副本，原主题 id 不变所以可一键还原。备选自动应用：违反"不静默覆盖"，否。

**取色器自绘（input[type=color] 外包一层壳），滑杆用原生 range 加样式。** DESIGN.md 已定系统控件自绘的基调，但取色器面板本体用浏览器原生弹层（够用、零成本），自绘的只是触发按钮与色值展示。备选完整自绘取色器：工程量与收益不成比，推迟。

## Risks / Trade-offs

- [cover 图跨域 canvas 取色被污染] → 优先走主进程下载后读文件字节，渲染进程不碰跨域 canvas
- [聚类对渐变 logo 取出色偏] → 取主簇的同时算色相方差，方差过大回落 favicon 或默认色
- [用户手动改 preferences.json 损坏] → 读失败回默认预设，不阻断启动
- [自定义主题增多后面板列表过长] → M2 不做搜索分组，列表溢出滚动，够用
